## 완료된 영역

### 여행 구성 및 온보딩

인솔자가 새 여행을 만들고 기간·구성원·모둠·장소를 채워 넣는 영역. 장소는 지도 검색으로
좌표를 확보하고 유래·문화유산 학습 콘텐츠를 붙일 수 있으며, 기존 엑셀 일정표나 종이
일정표 사진에서 데이터를 끌어오는 경로도 포함합니다.

- [x] 새 여행 생성 후 기간·구성원·모둠 입력 → 목록 화면에 카드로 표시
- [x] 장소 추가에서 이름 검색(Nominatim) → 후보 선택 → 핀 드래그로 좌표 미세조정 후 저장
- [x] 엑셀 일정표 가져오기 → 날짜·밴드·장소가 슬롯으로 채워짐
- [x] 좌표 없이 저장된 장소는 목록에서 "좌표 없음"으로 구분되어 다시 찾을 수 있음

관련: `src/pages/Setup.tsx`, `src/components/PlacePicker.tsx`, `src/components/ScheduleImport.tsx`, `src/excel.ts`, `src/ocr.ts`

### 일정 편성

하루를 조식·오전·중식·오후·석식·저녁 6밴드로 나눠 각 슬롯에 장소나 활동을 배치하는 영역.
식사 밴드도 활동 밴드와 동일하게 좌표 있는 식당 장소를 연결합니다.

- [x] 날짜별 6밴드에 장소 배치 → 일정 타임라인에 순서대로 표시
- [x] 식사 슬롯에서 식당 등록 → `kind: 'food'` 장소로 저장되고 슬롯의 `placeId`로 연결

### 실시간 지도 안내

여행 당일 "지금" 탭에서 오늘 동선·내 위치·다음 목적지까지의 도로 경로와 남은 시간을
실시간으로 확인하고 도착 알림을 받는 영역. 실 GPS와 이동 시뮬레이션을 토글할 수 있습니다.

- [x] 목적지 반경 80m 진입 시 도착 배너 + 진동, 다음 목적지로 자동 전환
- [x] OSRM 실패·오프라인 시 직선거리 추정치로 대체하고 "추정치" 라벨 표시
- [x] 첫 위치 수신 시 지도 refit, 반경 밖에서 진입한 경우에만 도착 처리

관련: `src/pages/Live.tsx`, `src/components/LiveMap.tsx`, `src/geo.ts`

## 남은 영역

### 0. 사진 정책 확정

**결정만 하는 단계입니다. 구현은 2번.**

사진을 "개인이 찍은 아무거나"에서 "장소별로 골라 남기는 기록"으로 성격을 바꿉니다.
장소마다 음식사진·단체사진·모둠사진을 **최대 4장까지만** 올릴 수 있게 제한합니다.

- [x] 4장 상한의 단위 — **장소당 전체 4장**으로 확정 (2026-07-17). 종류·모둠과 무관하게 한 장소에 총 4장
- [ ] 사진 종류(음식·단체·모둠) 분류를 필수로 할지, 선택으로 할지
- [ ] 상한 도달 시 동작 — 업로드 차단인가, 교체 유도인가

상한이 정해졌으므로 1-1의 용량 예측이 성립합니다. 남은 두 항목은 1-1을 막지 않습니다.

**왜 맨 앞인가:** 1-1(내보내기 포맷 설계)의 핵심 쟁점이 "사진 blob 포함 여부·용량"인데,
장소당 상한이 정해져야 용량 예측이 성립합니다. 상한 없이는 포맷 설계가 허공에 뜹니다.
결정 자체는 싸므로 먼저 끝냅니다.

`Photo` 테이블은 이미 `'++id, tripId, placeId, slotId'`로 인덱싱돼 있어(`src/db.ts`)
장소별 개수 제한을 거는 데 구조적 걸림돌이 없습니다.

### 1. 데이터 보존 및 공유

**최우선.**

여행 데이터가 기기 로컬(IndexedDB)에만 존재해 생기는 유실·단절 문제를 푸는 영역.
브라우저 데이터를 지우거나 기기를 잃으면 여행 기록이 통째로 사라집니다.

- [ ] **1-1 내보내기 포맷 설계** — 사진 blob 포함 여부·용량·포맷 버전. 0번이 전제
- [ ] **1-2 `exportTrip` / `importTrip` 구현** (`src/db.ts`) — 사진 포함 여행 1건이 내보내기 → 복원 후 원본과 일치
- [ ] **1-3 가져오기 시 ID 충돌 처리** — Dexie 자동증가 `number` ID 재할당과 참조(`slot.placeId`, `missionResult.missionId`, `photo.placeId`) 갱신. 같은 여행 2회 복원 후 "지금" 탭 경로 정상
- [ ] **1-4 UX** — 로컬 저장 경고 배너, 내보내기/가져오기 버튼, **여행 마지막 날 다운로드 선택 프롬프트**
- [ ] **1-5 e2e** — 내보내기 → 데이터 삭제 → 복원 시나리오가 `scripts/` 신규 스크립트에서 0 failed

**왜 최우선인가:** 되돌릴 수 없는 유일한 리스크입니다. 지도 API가 막히면 추정치로 버티고
알림이 안 오면 불편할 뿐이지만, 브라우저 데이터가 지워지면 사진·미션 점수·일정이 복구
수단 없이 사라집니다. 기능이 늘어날수록 잃을 것이 커집니다.

**1-3이 겉보기보다 까다롭습니다.** number ID는 재할당하면 이를 참조하는 모든 레코드를
따라가며 다시 매핑해야 합니다.

**"참가자가 일정을 받아 본다"가 여기 들어 있습니다.** 내보낸 파일을 카톡 등으로 전달해
참가자가 가져오기 하는 경로입니다 — 서버 없이 됩니다. 5번(링크 클릭 한 번에 실시간)과
혼동해서 같이 미루지 마세요. 1-2·1-4 설계 시 "참가자용 가져오기" 관점을 반드시 포함해야
합니다. 안 그러면 인솔자 전용 백업으로만 좁게 설계됩니다.

**1-4의 다운로드 프롬프트는 원래 "서버가 지우기 전 마지막 회수 기회"로 구상된 것**인데,
서버가 없는 지금은 의미가 더 또렷합니다 — 이게 유일한 백업 수단입니다.

### 2. 사진 정책 구현

0번에서 정한 정책을 코드로 옮깁니다.

- [ ] 장소별 업로드 상한 적용, 상한 도달 시 안내
- [ ] 사진 종류(음식·단체·모둠) 태그 저장 및 필터
- [ ] 기존 사진 마이그레이션 — 종류 미지정 사진 처리

관련: `src/pages/Gallery.tsx`, `src/db.ts`

### 3. 여행 이미지 합성

업로드된 여행 사진들을 편집해 **1~2장의 여행 이미지**로 만듭니다. Canvas 합성으로 끝나며
서버가 필요 없습니다.

- [ ] 여행 일정 마지막 즈음에 합성 이미지 제시
- [ ] 합성 결과를 저장·공유할 수 있음

2번의 종류 태그가 전제입니다 — 장소마다 음식 1장, 단체 1장 식으로 고르려면 분류가 있어야
합니다.

**로컬만으로는 값어치가 깎입니다.** 서버가 있으면 참가자 전원의 사진을 모아 합성하지만,
로컬만이면 내 기기에 있는 사진으로만 만듭니다. 실질적인 손실이니 5번 이후 재검토 대상입니다.

### 4. 알림 신뢰성

도착 알림과 위치 추적이 "앱이 열려 있을 때만" 동작하는 현재의 제약을 사용자에게 정직하게
드러내고, 가능한 범위에서 신뢰성을 높이는 영역. iOS PWA가 구조적으로 허용하지 않는
백그라운드 추적을 억지로 구현하는 것은 범위 밖입니다.

- [ ] 앱이 닫히면 알림이 오지 않는다는 점이 "지금" 탭에서 명확히 안내됨
- [ ] 주행 중 화면이 꺼지지 않게 유지 (Screen Wake Lock)
- [ ] 장시간 사용 시 위치 추적 정확도를 낮춰 배터리 소모를 줄이는 선택지

세 항목이 서로 독립이라 아무거나 먼저 해도 됩니다. 첫 항목은 안내 문구뿐이라 비용 대비
효과가 가장 큽니다.

### 5. "서버 없음" 원칙 재정의

**판단 대기. 0~4번이 끝난 뒤 착수합니다.**

지금까지 이 제품을 붙잡아온 진짜 병목은 낱개 기능이 아니라, **"서버 없음 원칙을 언제까지
어떤 형태로 지킬 것인가"라는 상위 결정이 한 번도 정식으로 내려진 적이 없다**는 것입니다.
아래 두 요청이 같은 벽에 부딪혀 멈춰 있습니다. 따로 판단하지 말고 한 안건으로 묶습니다.

**(a) 링크 공유 — 로그인 없이 링크만으로 참가 학생에게 정보 공유**

- [ ] 링크 클릭 한 번으로 참가자가 일정을 실시간 확인
- [ ] 참가자가 올린 사진이 인솔자에게 도달
- [ ] 여행 종료 후 다운로드 선택, 유예기간 뒤 서버에서 자동 삭제
- [ ] **원본 사진의 수명** — 사진은 여행 기간에만 서버에 두고, 슬라이드 제작이 끝나면 원본을 폐기 (2026-07-17 결정). 삭제 트리거는 **둘 다** 걸어야 함: 슬라이드 제작 완료 시 즉시 + 유예기간 만료 시 무조건. 제작 완료만 조건으로 걸면 인솔자가 슬라이드를 안 만들었을 때 영원히 남음
- [ ] **슬라이드 자체의 수명 — 미결.** 원본을 지워도 슬라이드에는 같은 얼굴이 그대로 들어 있어, 참가자 다운로드용으로 서버에 남겨두면 노출량이 실질적으로 줄지 않음. 원본 폐기가 상징적 제스처에 그치지 않으려면 슬라이드에도 수명이 필요하나, "참가자 전원이 받았는지"를 판정할 방법이 없음
- [ ] **슬라이드 제작 주체 — 미결.** 서버가 만들면 Vercel Functions 실행 시간 제한에 걸릴 수 있고, 인솔자 기기가 만들면 전체 사진을 그 기기로 내려받아야 해서 사진이 인솔자 기기에 남음. 열쇠(종단간 암호화) 방식을 택하면 서버가 내용을 못 보므로 자동으로 후자가 됨
- [ ] **미성년자 얼굴 사진·영상 보안:** 로그인 없이 링크만으로 진행될 때 "참가 학생들에게만" 접근을 실제로 보장하는 방법, 그리고 링크 유출 시 회수 수단(무효화, 재발급 등) 검토
- [ ] **다운로드 영상 링크의 보안 정책** — 동일한 접근 제한을 적용할지, 공개 다운로드로 할지 결정

**후보 접근: 여행 비밀번호** (2026-07-17 제안, 미검증)

여행을 만들 때 인솔자가 여행 비밀번호를 정하고, 링크에 들어온 사람이 그 비밀번호를 입력해야
정보·사진에 접근하게 하는 구조. 링크만으로는 못 들어오므로 유출된 링크 단독으로는 무력해지고,
계정 없음도 그대로 지켜집니다. 다만 착수 전에 아래를 풀어야 합니다.

- 링크와 비밀번호가 결국 같은 메시지(학급 단톡방)에 실려 두 요소가 한 요소가 되는 문제 —
  앱이 비밀번호를 링크에 싣지 않도록 강제하는 정도로 완화 가능하나 완전하지 않음
- 공유 비밀번호라 개인별 회수 불가 — 한 명이 흘리면 전체가 뚫리고, 바꾸면 전원에게 재공지
- 40명이 타이핑할 비밀번호는 약할 수밖에 없음 — 서버 쪽 시도 제한 필수
- 정당한 참가자의 재배포는 어떤 방법으로도 막을 수 없음 — 기대치를 그렇게 설정할 것

**갈림길: 비밀번호를 문지기로 쓸 것인가, 열쇠로 쓸 것인가**

- **문지기** — 서버가 비밀번호를 검증하고 사진을 내줌. 서버는 평문 보관. 구현이 단순하나
  Vercel과 DB 접근 권한자가 사진을 볼 수 있음
- **열쇠** — 비밀번호로 키를 파생해 기기에서 암호화 후 업로드. 서버는 암호문만 보관하고
  비밀번호는 서버에 도달하지 않음. 차별점이 "서버는 있지만 서버도 못 본다"로 되살아나며
  원래 약속의 계승이 됨. 대가는 비밀번호 분실 시 영구 소실(복구 경로 원리적으로 없음)과
  서버가 내용을 못 보므로 영상 제작이 반드시 로컬이어야 한다는 것 — 후자는 6번 구조와 일치

**(b) 지도 인프라 전환 — 공개 인스턴스에서 상용 API로**

- [ ] 단체 40명 동시 사용에도 검색·경로 호출이 차단되지 않음
- [x] 공급자를 바꿔도 `src/geo.ts` 밖의 코드는 수정하지 않음
- [ ] 국내 지명·상호 검색 결과가 Nominatim 대비 개선됨

**PRD 차별점 1번과 정면 충돌합니다:**

> 서버·계정·API 키가 전혀 없다 — 개인정보가 기기를 떠나지 않는다

이 한 문장에 **두 개의 다른 약속**이 뭉쳐 있습니다. "계정 없음"과 "서버 없음". (a)는 계정
없음을 지키면서 서버 없음만 포기하는 형태이고, (b)는 API 키 없음을 포기합니다. 착수 전에
PRD 차별점을 다시 써야 하며, 두 번 나눠 고칠 게 아니라 한 번에 정리해야 합니다.

**플랫폼: Vercel** (확정)

이미 Vercel에 정적 호스팅으로 배포돼 있어(`vercel.json`) 새 업체를 들이지 않습니다.

| 구성요소 | 용도 |
|---|---|
| Vercel Functions | 링크 기반 여행 데이터 API |
| Vercel Blob | 사진 저장 |
| Vercel KV / Postgres | 여행·일정 데이터 |
| Vercel Cron | 유예기간 지난 사진 자동 삭제 |

**"임시 보관"을 실제로 이행하는 건 Cron입니다.** 삭제가 사람의 행동(인솔자가 종료 버튼을
누르는 것)에 의존하면 그건 임시 보관이 아닙니다 — 안 누르면 미성년자 얼굴 사진이 서버에
무기한 남고 약속이 깨집니다. 자동 삭제가 이 설계의 핵심이지 부가 기능이 아닙니다.

**미결 사항:** 유예기간 길이, 개인정보 처리방침, 무료 티어 한계, (b)의 공급자 선택(카카오/네이버)과 API 키 배포 방법.

**1번이 5번의 전제입니다.** 1-1·1-2가 만드는 여행 직렬화 포맷이 곧 서버 동기화가 필요로
하는 포맷입니다. 순서를 뒤집으면 같은 것을 두 번 만들게 됩니다.

### 6. 슬라이드쇼 영상

**살림 (2026-07-17 결정).** 3번이 대체하지 않습니다 — 정적 이미지(3번)와 슬라이드쇼
영상(6번)을 둘 다 만듭니다. 촬영된 동영상을 다루는 게 아니라, 올라온 **사진들을 이어붙여
영상으로 만드는** 것입니다.

- [ ] 여행 사진을 로열티프리 음원과 함께 슬라이드쇼 영상으로 내보내기 — 로컬
- [ ] 제작된 영상을 참가자가 희망 시 다운로드 — **5번 의존**

음원 저작권 때문에 로열티프리 한정으로만 가능하고, 음원 라이선싱 + 인코딩으로 전체에서
가장 무거운 작업입니다.

**두 항목의 성격이 다릅니다.** 영상 제작 자체는 인솔자 기기 안에서 끝나므로 5번을 기다릴
필요가 없습니다. 하지만 참가자 다운로드는 영상이 남의 기기에 도달해야 하므로 배포 경로가
필요하고, 그게 곧 5번입니다. **이 배포가 5번의 보안 문제를 그대로 물려받습니다** — 링크를
아는 누구나 미성년자 단체사진으로 만든 영상을 받게 되는 구조입니다. 5번 (a)의 보안 항목을
같이 보세요.
